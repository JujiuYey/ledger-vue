# Architecture

Contributor-facing: how the package is built, the internal pipelines, and the invariants that must survive changes. The user-facing contracts these implement live in the guides; the design rationale is [DESIGN.md](DESIGN.md). This is the Vue edition of the React repository's architecture doc: same doctrine, and where Vue changed the mechanics — composables that run once, reactivity instead of re-renders — the paragraphs below describe what the Vue code actually does.

## Load-bearing internals

**Option partition, discipline instead of a type error.** Sugar mode splits props into behavior options vs presentation by the `DATA_TABLE_OPTION_KEYS` list in `data-table-types.ts`. The React edition's compile-time exhaustiveness (`satisfies` + `AssertNever` over the options type) has no counterpart for the array-form `defineProps` the SFC needs (the props include types Vue's compiler cannot resolve to runtime constructors, and the typed intersection is too large for the SFC compiler's type extraction), so the list lives next to the types it names and **a new `UseDataTableOptions` key must be added to it by hand** — forgetting means the option silently stays a presentation prop. What the runtime does check: in hook mode (`table` given), any behavior option beside `table` would be silently dead — the hook instance owns the behavior — so a dev warning names the dead keys. Controlled slices resolve through both halves of the Vue contract at once: the `onXChange` prop callbacks, and the `update:x` emits that `v-model:x` compiles to (each setter fires both, emit first).

**Composables run once; `ReactiveInput` replaces the re-render.** `useFoo` keeps its React name in a `.ts` file but is a composable called once per component in setup. Everything the React hook re-read every render becomes a `ReactiveInput<T>` (ref / getter / plain, read with `toValue()` inside computeds); `computed()` replaces `useMemo`+deps; `watch(..., { flush: "post" })` replaces commit-phase effects; `onScopeDispose` / `onUnmounted` replace effect cleanups. There is no `useEventCallback` and no replacement — closures defined in setup are stable by construction. The one input family that contract cannot cover is **handlers**: a plain handler IS a function, and `toValue` would call it to read its return value. `onEditCommit` / `onRowEditCommit` / `onRowReorder` therefore resolve through `isRef` checks alone (`ReactiveHandler` — a ref is unwrapped, anything else is taken as the handler itself), which still answers both identity and presence for a runtime swap: a component that must swap its handler passes it through a ref (`data-table.vue` wraps the props in `computed`s so both forms arrive); a `useDataTable` consumer passes the function. This is load-bearing — do not "fix" it to `toValue`.

**One erasure boundary.** `context.ts` erases `TData` for table-wide plumbing (labels, icons, row handlers, the active-row switch and its setter, the selection/expansion controllers, the column-filter set notification), and the internal render layer below it is `any`-bound as well (`erasedTable` in `data-table.vue`): TanStack v9's `in out` (invariant) generics make cross-instantiation unification of generic internals a fight with no type-safety payoff, so the erasure happens once at the root and the public surface stays strongly typed. Any new cast belongs *at that boundary*, not scattered through the tree.

**The committed table answers for the screen, because everything a commit decides with must outlive the editor that sent it.** The one shared core instance carries whatever the most recent options pass wrote, and everything the core derives follows: `getRow` and the row models, `getAllLeafColumns` and every `columnDef` on them, `options.meta.ledger`. The React edition needed `use-committed-table.ts` as a tearing guard against discarded renders; Vue's synchronous reactivity has none, so the module collapses to the invariant both editions share. As implemented: `useCommittedTable` hands out stable reader closures (`row`, `value`, `edit`, `has`, `columnIds`, `visibleColumnIds`, `canEdit`, `onScreen`, `isInstant`, `tableGate`, `column`) over one plain closure snapshot plus a `version: Ref<number>` bumped by every capture; `useDataTable` fills it in **one post-flush watch, `immediate: true`**, over the reactive inputs a commit-carrying change can arrive through — `managed.state`, `managed.columns`, `managed.data`, `enableEditing`, and `commitPresence` (the mode's commit-handler presence, watched separately so a handler swap reconciles the sessions even when no row-model input moved). The session controllers' `watch(committed.version, reconcile)` is the counterpart of the React edition's dependency-free every-render effect: bumped per capture, reconciled post-flush. Two rules follow, and both are load-bearing:

- **Event time reads the commit.** Every *editing* decision — the gate, `previousValue`, `validate`, where F2 enters, which column Tab moves to, whether a row is even there — resolves from the snapshot. "There" has two meanings and the snapshot keeps them apart: `row` reaches back to the pre-paginated and core models, because a session may legitimately name a row that is filtered out or has not arrived, while `onScreen` answers only for the rows that render. Values go through the *committed column's* `accessorFn` over the committed `row.original`, never `row.getValue`, which resolves its column through the core (upstream caches a row's values on the row object and rebuilds that cache only when `data` changes). Display order in the snapshot is pinned-aware (`start + center + end`), like everywhere else. And Tab resolves its destination **after** its commit succeeds, never when the key was pressed: an async write leaves the keyboard free, and a render landing while it is out can hide that column or shut its gate.
- **Render time reads the render.** `canEditCell` in `table-body.ts` reads the definitions and switches through the cell's own table, which is correct while a render is in progress — that *is* the render being drawn. The value a host hands `drafts.read` follows the same rule but not the same route: it comes from `cellValue(cell)` (`edit-meta.ts`), this render's column accessor over this row's `original`, **not** `cell.getValue()` — the same upstream value-cache staleness rule.

What this does **not** claim: the upstream mutation is untouched; the TanStack `row` / `column` handed to an application in a commit payload are the objects that render resolved, not reconstructions — a `Row` method the application calls itself still goes to the core.

**The table instance is not in the context.** The context is `provideDataTableContext` / `useDataTableContext` (a typed `InjectionKey`), and it carries the few table-wide facts the tree needs — each as its own field on a `reactive()` whose getters read the root's computeds, so a subtree redrawing without the root reads current answers without the context value ever churning. Handlers stay raw on it (`onRowClick` & co. read straight off `props`): Vue's identity churn does not cascade the way React's context re-renders do, so there is no revision machinery to defeat. What is not stable does not go there either — `renderDetailPanel` rides `meta.ledger` (a computed), so the body's render effect re-runs when it changes. The Styles API getter is *not* a context field: it is provided under its own key (`provideGetStyles`), because standalone compound components (the columns panel in a drawer) still need it.

**`use-slice.ts` is the controlled/uncontrolled contract, one computed wide.** `current` is a single computed: the controlled prop while the owner holds the slice (`!== undefined` — **`undefined` is the only "not controlled" signal, `null` is a value several slices legitimately hold**, the editing slices), the internal ref the moment it does not. `set` resolves its updater through `functionalUpdate` against what that computed says, writes the resolved value into the internal ref, and reports it (`onXChange` receiving the resolved value, never a function — plus the component's `update:x` emit in sugar mode). A mirror `watch` carries the owner's answer — accepted, normalized, or replaced — into the internal ref, so a later handover to uncontrolled departs from the owner's last word; equality writes are no-ops by ref semantics, so an acceptance echo costs nothing. **Silence is a refusal**: the on-screen value never echoes a request the owner declined, and the next event departs from what is on screen. The React edition's requested-value ledger existed only to keep updaters honest across React's commit windows, which Vue's synchronous reactivity does not have; it is gone, and the contract is verbatim.

**Editing sessions live in the controller layer, not in the editors.** One module each — `use-cell-editing.ts`, `use-row-editing.ts`, `use-instant-editing.ts` — and `useDataTable` only assembles them: each takes the committed snapshot and its slice, and returns a stable surface `meta.ledger.editing` composes. A mounted editor is a *view* of one plus a keyboard surface. This is not tidiness — an editor is unmountable at any moment (virtual scrolling, a hidden column) while the session is not, and every previous defect in this area came from a session fact living somewhere a scroll could delete. The session owns the pending draft, what it has already written, the in-flight commit and its ownership, the pending flag, the error, whether the gate was lost, and whether it has settled. The editor owns only what is genuinely per-instance: its DOM node, focus, and its own unmount. An instant column is the same rule with no session in it: a change *is* the commit, so the controller is addressed by *target* — nested by row and then column, never a joined key, because row and column ids are opaque application strings and any separator is one an id may contain.

Vue mechanics inside that doctrine, all deliberate: React's refs are plain closure bindings; the **epoch is a `ref`** the render layer tracks reactively (the counterpart of React's per-epoch callback identity — whether an editor may be on screen is part of the render output, so a session ending without the slice moving has to be a reactive change); and React's two commit-phase effects run as **one post-flush watch on the slice plus a `queueMicrotask` first pass** (the deferred pass matters: `committed` is captured by `useDataTable` after the table exists, and a session a controlled application names up front must be reconciled against that capture, not the empty snapshot setup starts with). Invariants that must survive changes, each pinned by the suite:

- **The slice is a request, not a fact.** `start`, `stop`, and every trigger only ask; session boundaries are keyed in the post-flush reconciliation against what actually rendered, and an application that declines to move the prop keeps a live session on the target it named. A boundary ends the session **whole** — token, in-flight ownership, pending flag, drafts, error, and the armed unmount together.
- **What an editor shows comes from the session, never from a copy taken at mount.** `read(rowId, columnId, source)` answers with the pending value if there is one, else what the session has written, else the cell's own.
- **A session remembers its own writes, until the data moves.** A successful commit records what it carried against the value the data read at the time; once the data moves past that, the record retires *permanently*. The reconciliation also remembers movement *during* an in-flight request (`writing.moved`), including out and back again, which comparing at settle time could never see.
- **`previousValues` is what the application last knew**; a column whose definition disappears falls back to the last effective previous the session observed for it (row mode records these on every sighting — that record is also how a gate closing on a column this session was editing is told apart from a responsive breakpoint taking the column away).
- **Only the settlement that still speaks for the session may act on it.** Requests carry a session token; a settled request whose session has ended reports failure and touches nothing. A commit that lands behind a value typed since keeps the editor open.
- **Two gates, and the render owns one of them.** An editor host renders only if the cell may be edited *now* (eligibility, asked in the render itself — `edit.enabled` is application code) **and** the session is live (`active`, a controller read keyed to the epoch — a session fact that cannot be asked during render). `data-editing` follows the gates, not the slice.
- **Losing eligibility latches**, and reconciliation is idempotent per session; a **command** (Escape, `stopEditing`, a `startEditing` that must leave the cancelled session first) is never idempotent — it asks again, and the commit a command runs re-reads the gate rather than trusting what the session opened on.
- **The unmount-commit defers one tick** so a remount of the same cell — the virtualizer re-mounting a row still in view — cancels it; only a real departure commits, and once nothing is mounted any failure degrades to discard because there is nowhere left to report it.

**Sorting, selection and expansion toggles carry their render with them.** v9 computes half of each toggle *outside* the updater it hands the state setter, and that half reads the shared core, while the updater's own `old` is correctly the committed value. `toggle-fns.ts` is those updater bodies transcribed as pure functions, reading nothing but structural row properties and the rules its caller resolved; `use-row-commands.ts` resolves those rules and the row order in the **same post-flush watch that captures the committed table** (`captureRows` rides the capture), and exposes two stable controllers. The Shift anchor moved with them: v9 keeps it on the core instance (`_lastSelectedRowId`), the one object every options pass rewrites. A feature's `getDefaultTableOptions` is merged into the **core's** options, not the adapter wrapper's, so `isMultiSortEvent` is defaulted at the header rather than read blindly — a consumer override through `tableOptions` still wins.

**State reads inside the library go through `table.atoms.<slice>.get()`, and the atoms must be *tracked* reads.** `table.state` is not reactive (the vue-table adapter bridges state slices into Vue atoms precisely so computeds can depend on them), so every computed that derives from layout — the display columns, the row counts, the colgroup — starts with explicit `table.atoms.<slice>.get()` calls naming the slices it depends on, *then* calls the memoized model API. Omit the atom reads and the computed silently stops updating; this is the most common port bug class. One mount-time oddity is also load-bearing: `useDataTable` performs a single synchronous `table.setOptions(previous => ({ ...previous }))` identity bounce after `useTable`, because the adapter's option-propagation watches can let the first generation of table-core memos compute against a half-bridged state (observed live: a column missing from `getVisibleLeafColumns()` while its own `getIsVisible()` was true) — one bounce invalidates every memo before the first render reads it.

**Header, body, and footer are separate tables under one ARIA table.** The header (and, when any column declares a `footer`, the totals region) sits in an `overflow: hidden` viewport outside the body scroller, so the vertical scrollbar spans exactly the rows and totals stay visible. Three invariants keep the tables pixel-equal: identical `getStyles("table")` answers (one shared `tableProps` computed: `table-layout: fixed`, `border-collapse: separate` inline because a host's unlayered `collapse` would win, and collapse drops borders on sticky cells), the one shared `<colgroup>` spec, and the root-level column variables. Horizontal sync is one assignment — the body's scroll event mirrors `scrollLeft` onto the header and footer viewports in the same frame; native non-passive wheel listeners forward **dominantly horizontal** deltas (`|deltaX| > |deltaY|`) from those regions to the body. The body viewport is `overscroll-behavior: none` (merged through `viewportProps`): rubber-band overscroll translates the body past the clamped scroll position the mirrors read. Because the native tables would split the semantics, all are `role="presentation"` and the explicit ARIA table lives on `main` with `row` / `columnheader` / `cell` roles on the parts — keep those roles when adding new row kinds.

The scroller is reka-ui's ScrollArea (the Vue port of the Radix primitives Mantine's ScrollArea wraps in the React edition). Its Viewport component renders the scrolling div itself, so **the element every ledger mechanism keys on — the scroll mirror, the virtualizer, row scrolling, `onEndReached`, the width engine's ResizeObserver — is the component's exposed `viewportElement`, bridged into `viewportRef` by a watch**. Two recorded reka specifics: `type="always"`, not `"hover"` (reka's hover variant unmounts the bars when idle and its `forceMount` never reaches the nested Presence, parking the viewport at `overflow: hidden` until the first pointerenter — the hover *reveal* rides CSS on the wrapper instead), and per-axis scrollbar presence is the component's own `data-hidden` signal (`scrollWidth > clientWidth` per axis, integer comparison — sub-pixel table widths otherwise read as hairline overflow and reka keeps a full-looking thumb mounted on an axis that cannot scroll).

**Borders are three edges, each drawn once** ([styling.md](styling.md#borders)): row separators sit between rows and never under the last one (the body marks its final display row — and a `spanRows` anchor ending on it — with `data-last`); the closing line is the opt-in `withBottomBorder`; the `withTableBorder` frame is four real borders on `main` and owns every edge.

**Column geometry is CSS variables, and the numbers come from the width engine.** `use-column-widths.ts` resolves every visible leaf column to exact integer pixels ([sizing.md](sizing.md)); widths (`--ledger-col-width-<id>`) and pinned offsets (`--ledger-col-start/after-<id>`, summed from the same resolved numbers) are written once at root level; `<col>` elements (in every region's table) and pinned cells reference them; the tables' own `width` is the exact total. A resize drag writes the `columnSizing` slice (through `table.setColumnSizing`), and the header cell receives `columnWidths` / `columnSizing` as **props** — the render that drew the handle owns the numbers the drag departs from, never an event-time table read. There are no React row-memo tokens to protect; the Vue counterpart of that economy is that the body's render effect reads only what a row draws (its geometry arrives as CSS variables, never as tracked width numbers), plus the **stable render host**: a TanStack/application renderer is mounted through a tiny `FlexRenderHost` functional component (`source: () => flexRender(...)`), because a fresh `h(() => ...)` closure per cell would change the component type on every patch and tear the subtree down. Three engine invariants:

- **Author sizing is read from the raw-definition registry** (`rawColumnSizing` in `build-columns.ts`, keyed off the per-leaf meta clone created during preprocessing), never from `column.columnDef` — TanStack merges `size: 150, minSize: 20` defaults into every resolved definition, which makes "the author declared no size" unrepresentable after the merge.
- **Display order is pinned-aware everywhere**: the colgroup, the width specs, and the offset sums all use the `start + center + end` concatenation, never bare `getVisibleLeafColumns()`, or a mid-table pinned column drifts onto its neighbor's `<col>`.
- **A resize handler carries its whole render with it.** The column, the width on screen, the constraints, and the `columnSizing` entry Escape restores all arrive as a `ResizerSpec` built by the render that drew the handle (`autosize-column.ts` takes the same spec); the session asks the table for *nothing* at event time. The one thing it re-reads is whether its handle is still on screen, resolved by column id **within the table that started the drag** (`.ledger-main`-scoped selector — a captured node is replaced whenever the header re-renders, which a live drag does on every move). A column that really leaves mid-drag ends the session.

**Column virtualization rides the same engine, not a second virtualizer** ([virtualization.md](virtualization.md#column-virtualization)). Only the center zone windows (pinned columns are sticky and always mounted); the window is a binary search over the engine's prefix sums, derived in the same render pass that draws the colgroup — a measuring virtualizer would hold a parallel copy of the horizontal geometry that resize, responsive breakpoints, and grow redistribution would each have to invalidate by hand. The hidden center runs collapse into two spacer `<col>`s with the exact widths the missing columns add up to, so the three synced tables keep full scroll width and honest pinned offsets. Scroll-driven window shifts write the newest window outright — Vue's scheduler coalesces same-tick writes into one render, which is the time-sliced behavior the React edition had to build with transitions — and a commit-step re-measure keeps a smooth scroll chasing the live position; a discrete leap larger than the visible strip (or a target that no longer overlaps the committed window) applies synchronously so a landing is never blank.

**The Styles API is one pure function, provided to the tree.** `createGetStyles` (`get-styles.ts`) merges, per selector: `class` = the static kebab-case class (`dataTableClasses`), then the call's own `className`, then the consumer's `classNames[selector]`, then — root only — the consumer's `className` prop; `style` = the call's own style (CSS variables, geometry), then `styles[selector]`, then — root only — the consumer's `style` prop, so an author can always win; `attributes` pass through onto every element they are spread onto. The resolved getter is a computed of the root's style props and is provided once (`provideGetStyles`); parts inject it (`useGetStyles`, falling back to static classes outside a table). There is no revision/refreeze machinery — `use-styles-revision.ts` existed only to defeat React re-render cascades (a recorded omission: the getter's identity is stable for as long as its inputs are).

**The stylesheet owns the design tokens.** Everything lives in `@layer ledger`; classes are kebab-case under `ledger-`; state is data-attributes, never state classes. This edition has no host theme, so the `--ledger-*` tokens are *defined in the file itself* — light values on `:root` and `.ledger-root` (teleported popover panels mount outside the root and still have to resolve every `var()`), dark values under `html[data-color-scheme="dark"]` and `.ledger-root[data-color-scheme="dark"]` (the per-instance `colorScheme` prop), with the OS preference (`prefers-color-scheme`, gated on `html:not([data-color-scheme="light"])`) carrying dark until the attribute speaks. Row backgrounds flow through the same pipeline as the React edition — stripe/hover/selected set `--ledger-row-bg` on the row, the paint site is `.ledger-row > td`, pinned cells follow it — so the "pinned column doesn't cover stripes" defect stays unrepresentable; keep any new row tint inside it. A root-level guard spec (`styles-tokens.test.ts`, which lives at repo root because it reads files through `node:fs` and the package tsconfigs carry `types: []`) fails the build at the first `var(--ledger-…)` reference that has no definition and no fallback — a token that silently resolves to nothing was the invisible-scrollbar bug, and geometry probes never catch it.

**Display rows.** `buildDisplayRows` (`table-body.ts`) interleaves data rows and expanded detail-panel rows inside each top/center/bottom zone. The virtualizer counts the center list; pinned lists remain mounted and use the same one-row-per-item measurement model. Virtualization renders top/bottom spacer `<tr>`s (geometry only, `data-ledger-spacer`) around the window — never absolute positioning, so the real-`<table>` guarantee holds. ARIA indexes concatenate header, all three body sequences, loader, and footer into one logical table even when the center DOM is windowed.

**Pinned rows measure, never assume.** Sticky offsets are the measured cumulative heights of preceding pinned data/detail items, ResizeObserver-tracked (`use-pinned-row-offsets.ts`); how many items each end holds is mirrored in a **post-flush watch**, and the measurement works from that mirror rather than from the props; a ref callback writes its element whatever the array's current length is. The header lives outside the scroller, so top offsets start at 0. A shared `top` stacks every pinned row onto one edge — found by the interactive browser pass; jsdom cannot express it.

**The active row and the imperative scroll answer from the render on screen.** Arrow keys, `Home`/`End`, the live-region announcement and `scrollToRow` all read one `DisplaySnapshot` — a `computed` in `data-table.vue` (`display-snapshot.ts`): the pinned-aware `top + center + bottom` order, the centre zone the virtualizer indexes, the page's own model that `scrollToIndex` counts through, and the leading data column that names a row to a reader. Each read is TanStack-memoized, so holding the snapshot costs nothing per scroll step, and the handlers are stable closures over the ref, so they always see the newest computed. The announcement names the row through that column's own `accessorFn`, for the same reason `cellValue` exists; it is written imperatively (a live region wants a text change, not a re-render), and the mount run rides `onMounted` because a `defaultActiveRowId` present from the first render never moves a dependency.

**Storage and the environment are trust boundaries, and both fail quietly.** `persistState` serializes in the reactive pass that produced the state but can never throw out of it; an unserializable state cancels the pending write rather than leaving the previous payload standing in for the current state, and says so once in dev. Reading back is the mirror: shape guards decide whether a slice can be used at all, and `columnPinning` is additionally repaired to unique-and-disjoint (a pinned id repeated within a side — or claimed by both — draws the column twice). `isDev` reads `process.env.NODE_ENV` **unguarded** and catches the failure (`env.ts`) — Vite substitutes that expression textually in client code, library source served through the `source` condition included, so a `typeof process` guard in front of it silences every dev warning in the browser where developers read them. `env.ts` stays dependency-free so its test can stub `process` without re-evaluating the graph.

**Infinite loading and layout races.** `onEndReached`'s probe and the unconstrained-virtualization warning both run one `requestAnimationFrame` after the watched inputs change (a watch with `onCleanup` cancelling the frame) and ignore unlaid-out viewports (`clientHeight === 0`) — the pre-layout frame reads as "at the bottom" and used to fire phantom loads. The once-per-data guard keys on the data's *identity*, not its length.

## Testing strategy

Vitest 4 + jsdom + `@vue/test-utils` (Testing Library is also available); specs colocated as `<name>.test.ts` next to their source; tests run from the **repo root** (the root `vitest.config.ts` aliases the workspace packages to their TypeScript/Vue sources — subpath aliases first, because a bare alias would prefix-match `./styles.css` onto `./src/index.ts`; two guard specs live at root because they read files through `node:fs`). Component specs mount real harnesses: `mount(Harness, { attachTo: host })` with the host div appended to `document.body` (jsdom has no layout, but attached DOM is what teleported popovers, `useId`, and drag targets resolve against), `enableAutoUnmount(afterEach)`, and every state assertion behind `await nextTick()` (composables that need a setup scope — all of `useDataTable`'s family — mount through a tiny `useTableInSetup` host). Recorded jsdom techniques the suite depends on:

- **jsdom 26 implements neither layout nor `PointerEvent`.** Pointer-driven code (resize, header reorder, the truncate hover) is driven with `MouseEvent` carrying the pointer type string; `getBoundingClientRect` is stubbed where geometry decides (the columns-panel drag stubs the rows' rects to their natural stacked geometry).
- **dnd-kit paths are driven by intercepting `Monitor.prototype.addEventListener`** (`columns-panel-drag.test.ts`): the probe instantiates a `DragDropManager`, wraps the monitor prototype's `addEventListener` to capture the app-registered listeners, then invokes them with crafted drag events exactly as a real drag would deliver them — the pointer sensor itself needs layout.
- **`wrapper.vm.setupState` proxies lie** — never read setup bindings through the wrapper; reach the table through the exposed imperative handle (`handleRef`) or a harness-owned binding (the `__testTable` global), and read state through `table.atoms.<slice>.get()` after a tick.
- **`table.options.meta` is a computed riding the options object; raw options reads are not a reactive route.** The vue-table adapter unwraps refs/computeds at the *top level* of the options only, and re-syncs on watch ticks — so tests read `meta.ledger` through a fresh accessor call (`() => table.options.meta?.ledger`) rather than holding the object, and anything that must be current reads atoms and ticks.

What jsdom cannot express — real geometry (pinned-row stacking, scroll windows, adaptive resize, edge shadows) — is verified interactively in the playground with a real browser; when touching those areas, run the relevant demo and scroll/drag it. **Dragging is in that category**: dnd-kit's pointer sensor needs layout, so the drag mechanics are pinned through the listener-capture suite above and the pure order math in `column-order.test.ts`; the felt drag itself belongs to the browser pass.

`it.todo` is the recorded-deviation mechanism: where a React scenario is built on `startTransition`/Suspense throwaway renders — machinery Vue does not have — the test lands as a todo whose *name carries the reason*, so the deviation lives in the suite itself. The tally: **twelve React-concurrency scenarios** across cell, instant, and row editing, plus **one true deferral** — the `table`-prop instance swap (`instant-editing.test.ts`): an SFC captures `props.table` once at setup, so swapping the instance for another mid-life is unsupported, and a consumer who must exchange instances remounts with `:key`. `grep -r "it.todo" packages/vue/src` audits the count; anything not in those thirteen is a missing test, not a recorded deviation. `vitest/warn-todo` is off in `.oxlintrc.json` for exactly this reason.

Gates (all must stay green): `pnpm test`, `pnpm typecheck` (root `tsc` for repo-level files + per-package `vue-tsc` — templates are typechecked here), `pnpm lint:check` (**oxlint, not ESLint** — the sealed `@coldsmirk/eslint-config` has no Vue axis, and composing `vue-eslint-plugin` under a sealed config was judged worse than a native linter reading `.ts` and `.vue` script blocks out of the box; a recorded decision, see [DESIGN.md](DESIGN.md)). `.oxlintrc.json`: typescript / unicorn / import / jsdoc / vitest plugins, correctness + suspicious as errors; turned off on purpose are `import/no-named-as-default` (the `clsx` import mirrors the React source), `import/no-unassigned-import` (CSS side-effect imports are the documented pattern), and `unicorn/consistent-function-scoping` (colocation mirrors the ported file structure); `no-shadow` allows `_`. `.vue` templates stay unlinted — `vue-tsc` typechecks their expressions. Then `pnpm lint:css:check` (Stylelint on the sealed plain-CSS `@coldsmirk/stylelint-config` — the kebab-case class contract, enforced mechanically), `pnpm build`, `pnpm check:package`. Tests run against source through the aliases above — a green suite does not prove the build; the last two gates do.

## Build and release

Vite (`@vitejs/plugin-vue`) building the two entries (`index`, `locales`) as ESM + CJS, all runtime dependencies externalized (`vue`, the TanStack adapters, `clsx`, `@dnd-kit/dom`, `reka-ui` — the last was found silently bundled while also declared a dependency, and is external now), `cssCodeSplit: false` with `styles.css` shipped as a named asset and copied verbatim, `sideEffects: ["*.css"]`, exports map with a `source` condition (Vitest and the playground alias to source explicitly). Declarations bundle through **`vite-plugin-dts@4` in `rollupTypes` mode** (api-extractor underneath): one self-contained `index.d.ts` / `locales.d.ts` per entry — `vue-tsc`'s per-file emit keeps extensionless relative imports, which fail attw's `node16` resolutions, the same failure mode that makes the React edition bundle through tsdown. `.d.cts` twins are copied beside each `.d.ts` for the `require` conditions (`vue-tsc` only emits `.d.ts`, and publint checks both). The version is pinned at 4 on purpose: **vite-plugin-dts 5.x silently dropped `rollupTypes`** — it accepts the option and emits per-file declarations, which attw then fails; do not "update" past 4 without checking that. `pnpm check:package` runs publint + attw against the packed output (`packages/vue/.attw.json` skips the typeless `styles.css` entrypoint, profile `node16`). Husky wires the gates: commit-msg → commitlint (single-line Conventional Commits), pre-commit → both lint checks (oxlint lints the whole repo in milliseconds, so there is no lint-staged), pre-push → typecheck + test. Lockstep versioning via `scripts/version.ts` (`pnpm version:patch|minor|major`); `ci.yml` runs the same six-step gate.
